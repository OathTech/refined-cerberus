### M-2 (Medium — header claim over-general at a boundary K3 will meet): the "SUCCESS" equivalence (i) is stated for `allocateRegion` including size 0, where it fails at `lastAddress ≤ 0`

- Claim. Heap.lean budget header (2072-2083, verbatim): "`size` the
  byte count (`(sizeofCtype ty).max 1` for an object, `sizeN.toNat` for
  a region) … (i) SUCCESS. `alignedAddr ≠ 0 ↔ size + align ≤
  lastAddress`, i.e. `allocCost = size + align − 1 ≤ headroom =
  lastAddress − 1` (`freshBase_ne_zero_of_cost`, the sufficient
  direction the rules use)." Notes §2 (i) and WALKTHROUGH §4 repeat the
  chain "alignedAddr ≠ 0 ↔ size + align ≤ lastAddress ↔ allocCost ≤
  headroom" (WALKTHROUGH states it for `allocateObject` only, which is
  fine).
- Tree's truth. The first `↔` holds for every size (`toNat (la − size) ≥
  align ↔ la − size ≥ align` since `align ≥ 1`). The "i.e." step is in
  `Nat` with `headroom la := (la − 1).toNat`: at `size = 0`, `align = 1`,
  `la ≤ 0` the cost is `0 ≤ 0 = headroom la` yet `size + align = 1 > la`
  and the engine kills. Decided in the audited environment:
  `example : freshBase 0 1 0 = 0 := by decide` and
  `example : (0 + (1:Int).toNat.max 1 - 1 ≤ headroom 0) := by decide`
  both succeed. The THEOREM is right: `freshBase_ne_zero_of_cost` carries
  `(hsz : 0 < size)`, which excludes the case; `allocateObject` pads to
  `max 1` and `create_atomic` requires `0 < sizeof ty`. So K2.5's rules
  are sound; the prose generalises past what the theorem says, in the
  very sentence that says "the same arithmetic in both".
- Consequence. K3 (`allocateRegion`, which admits `size = 0` — K0
  notes/K0 audit N-1) cannot reuse `freshBase_ne_zero_of_cost` for
  zero-size regions as stated, and cannot get `la ≥ 1` from `MemWF`
  (`la_wf : σ.lastAddress ≤ 2 ^ 64` bounds above only). `la ≥ 1` IS an
  engine invariant (every successful allocation sets `lastAddress :=
  alignedAddr ≠ 0`, and `alignedAddr ≥ 0`), just not a recorded one. A
  K3 region rule priced at `max al 1 − 1` for size-0 regions would be
  unsound without one of the two premises.
- Fix. In the header (and notes §2 (i)), qualify: "(i) holds as stated
  for the first `↔`; the reading `allocCost ≤ headroom` is equivalent
  under `0 < size` (the object rules' `hsz`) or `1 ≤ lastAddress`"; and
  register for K3: either the region rule carries `0 < size`, or `MemWF`
  gains `1 ≤ lastAddress` (engine fact: `allocateObject`/`allocateRegion`
  :1522/:1546 set `lastAddress := alignedAddr` with `alignedAddr ≠ 0`).

### 3. THE ENGINE BOUND

Pinned engine, verbatim (`CerbMem.lean`): `def alignDown (addr align :
Nat) : Nat := (addr / align) * align` (:1451); `allocateObject`: `let
align := alignN.toNat.max 1`, `let size := (sizeofCtype tagDefs ty).max
1`, `let addrAfterSize := st.lastAddress - size`, `let alignedAddr :=
(alignDown addrAfterSize.toNat align : Int)`, `if alignedAddr == 0 then
(NDkilled (Other (MerrOther "out of memory")), st) else …
lastAddress := alignedAddr …` (:1509-1522); `allocateRegion`: same with
`let size := sizeN.toNat` and `dynamicAddrs := alignedAddr ::
st.dynamicAddrs` (:1537-1548). `freshBase la alignN size := alignDown (la
− size).toNat (alignN.toNat.max 1)` (Heap.lean 1325) mirrors it exactly
(`Int` subtraction then `toNat`, as the engine).

Soundness of `allocCost = size + max al 1 − 1` for every residue: on
success `la − size ≥ align ≥ 1`, so `(la − size).toNat = la − size` and
`freshBase = (la − size) − ((la − size) mod align)`; the descent is `size
+ r` with `0 ≤ r ≤ align − 1`, so `≤ allocCost` — worst case `r = align
− 1`, i.e. `la − size ≡ −1 (mod align)`. Checked at the boundary in the
audited environment: `freshBase 33 16 2 = 16` (descent 17 = cost 17,
tight; new headroom 15 = 32 − 17), `freshBase 17 16 1 = 16` (cost 16 =
headroom 16, success), `freshBase 17 16 2 = 0` (cost 17 > 16, killed).
The cursor ≡ 1 (mod al) case (`la = 17, al = 16`) behaves as the theorem
says. `freshBase_ne_zero_of_cost` is correct (kernel `omega` after
`Nat.div_add_mod`/`Nat.mod_lt`; axioms `[propext, Quot.sound]`).

Failure condition: `alignedAddr = alignDown … ≥ 0` always, so
`alignedAddr == 0` is the ONLY failure; there is no negative/underflow
case — `Int` underflow of `la − size` is absorbed by `.toNat` into the
`0` case, which the kill arm covers. `headroom la := (la − 1).toNat`
matches: for `size > 0`, `alignedAddr ≠ 0 ↔ size + align ≤ la ↔ size +
align − 1 ≤ (la − 1).toNat` (both sides force `la ≥ 1`). Size-0 region
(`allocateRegion`, `sizeN = 0`): cost `= max al 1 − 1`; the bound is
sound whenever `la ≥ 1` (`alignDown la align ≠ 0 ↔ align ≤ la ↔ align −
1 ≤ la − 1`) and FAILS at `la ≤ 0, align = 1` (M-2). K2.5's theorem
carries `hsz`, so the tree is sound; the header's prose is not (M-2).
