## 2. The coupling inequality and the engine bound

THE ENGINE, verbatim from the pinned `CerbMem.lean` — `allocateObject`
:1504-1531 and `allocateRegion` :1533-1551 share the arithmetic:

```
    let align := alignN.toNat.max 1                                  -- :1509 / :1537
```

Definitions (Heap.lean, section "The allocation budget — the pure engine
bound"): `allocCost tds ty al := sizeofCtype tds ty + al.toNat.max 1 - 1`,
`headroom la := (la - 1).toNat`, `planCost tds : List AllocReq → Nat` (the
summed costs; `AllocReq` is kept as the pure request record for the
plan-shaped statements). THE COUPLING INEQUALITY: the authority `B` satisfies
`B ≤ headroom lastAddress` — stated in the state interpretation through the
cursor cell (which `CohG.cursor` ties to the real `lastAddress`):


The cursor's EXCLUSIVE FRAGMENT `cursorOwn c` lives inside this conjunct
since K2.5: no client owns the cursor any more (the budget only needs the
bound; the exact value stays tracked by `CohG.cursor`/`MemWF.cursor_lo`), and

the allocation-aware launch takes the right one (`budgetInterp_intro`). `CohG`
itself is UNCHANGED (K0's conditional structure kept — one change at a time).

THE TWO ARITHMETIC FACTS, proved (Heap.lean, kernel-only, `omega` after
`Nat.div_add_mod`/`Nat.mod_lt` — sub-trio cones `[propext, Quot.sound]`):

```lean
theorem freshBase_ne_zero_of_cost (la al : Int) (size : Nat) (hsz : 0 < size)
    (h : size + al.toNat.max 1 - 1 ≤ headroom la) :
    freshBase la al size ≠ 0
theorem headroom_freshBase (la al : Int) (size : Nat) (hsz : 0 < size)
    (h : size + al.toNat.max 1 - 1 ≤ headroom la) :
    headroom la ≤ headroom (freshBase la al size) + (size + al.toNat.max 1 - 1)
```

(i) SUCCESS: `alignedAddr ≠ 0 ↔ size + align ≤ lastAddress ↔ allocCost ≤
headroom` — the exact condition; the rules use the sufficient direction.
(ii) CONSUMPTION: the cursor descends by exactly `size + (lastAddress − size)
% align ≤ size + align − 1 = allocCost`, so the headroom shrinks by at most
the cost. `allocCost` is therefore the EXACT engine cost in the sense the
brief asked ("or the exact engine cost if tighter"): it is the tightest
ORDER-FREE bound — the exact descent depends on the cursor's residue modulo
the alignment, i.e. on the sequence of preceding requests, so no
order-independent cost is tighter. `allocCost_pos`: a real object type has
positive cost, so `allocBudget 0` buys nothing.

The atomic rule's proof (`create_atomic`, Rules.lean): a fragment is at most
the authority (`budgetAuth_bound`), the authority at most the headroom, hence
`hnz := freshBase_ne_zero_of_cost` and `allocateObject_success` applies;
after the step `budgetAuth_consume` removes the cost from the authority and
`headroom_freshBase` shows the new headroom still bounds it; the cursor cell
is advanced with `cursorHeap_update` (the fragment came out of the
interpretation and goes back in). `MemWF.la_wf` (through `CohG.wf` under the
cursor's presence) supplies the `addrOf p < 2^64` bound the plan's
`c.lastAddr ≤ 2^64` used to carry.

## 5. What the restatement means — honest classification

At the RULE level the budget is strictly more general: a client may hold any
budget `≥` the cost (`allocBudget_le`), split it across ∗ in any order, and
an allocating callee's precondition is simply its own budget (the
calls-arc motive). At the LAUNCH level the two premises are NOT
interderivable, in EITHER direction, and this is a measured fact about the
engine's arithmetic, not a proof gap:

- budget ⇒ plan: a budget `planCost reqs ≤ headroom` guarantees the plan
  fits in any order (each request consumes at most its cost — §2 (ii)).
- plan ⇏ budget: a plan can fit where the summed costs exceed the headroom.
  Cursor `32`, requests `⟨16, 16 bytes⟩` then `⟨8, 8 bytes⟩`: the plan runs
  `alignDown (32 − 16) 16 = 16 ≠ 0`, then `alignDown (16 − 8) 8 = 8 ≠ 0` —
  fits; the costs sum to `(16 + 16 − 1) + (8 + 8 − 1) = 46 > 31 = headroom`.

So for a given program the set of INITIAL STATES the new `MemTripleU_alloc`
covers (those with `headroom ≥ Σ allocCost`) is a SUBSET of the set the plan
form covered — the budget is conservative by up to `align − 1` bytes per
allocation, the price of an order-free bound. At any realistic cursor the
slack is irrelevant: the production cold start has `headroom prodMem₀.lastAddress
= errnoAddr − 1 = 281474976710647 = 2^48 − 9` against budgets of 7, 23 and 46
bytes. The statements are STRICTLY MORE GENERAL in the RESOURCE (any budget
≥ the cost, any split, any order) and slightly less general in the launch
premise; this note is the record of that trade ([AGENT], per the brief's
"take the snapshot; every changed public statement must be exactly plan →
budget").
