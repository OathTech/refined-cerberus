## 4. The report's first run — a real catch, and the mapping choice

The first run mapped `Frag.load → wps_load` and came back RED:
`wps_load` (the whole-cell load rule at the statement stratum) lies
in NO exhibit module's proof cone. The exhibits' loads flow through
`wps_load_at` (the generic typed-subrange form: Array/ListRev/TreeRot)
or the base-logic `wp_load` (Exhibit.lean). The old manifest listed
all four load rules in one cell and passed because ANY of them
sufficed. The mapping now names `wps_load_at`. [AGENT] observation,
not a logical gap: `wps_load` is a proved but client-less rule
(`wps_load_at` generalizes it); it stays pinned exact in Audit. Same
shape, not red: `wps_store` is consumed by LoopExhibit only — the
other stores flow through `wps_store_cell_at`/`wp_store`/`wpt_*`.

Committed report (`docs/CAPABILITY_MANIFEST.md`): 18 rows, 0 red,
13 exhibit modules. `Exhibit`/`ProdExhibit`/`ProdLoopExhibit`/
`DivergeExhibit` appear in no consumer column because their proofs
use the `wp_*`/`wpt_*` strata rather than the mapped `wps_*` rules
— a limitation of the one-rule-per-row form, accepted (the report is
a speedbump, not a coverage certificate).
